Problem 1: Decimal Precision

  • Fractions such as 0.1, 0.2, 1.255, and 10.075 are simple in base 10 but often repeating in base 2.
  • A binary64 value stores the nearest representable binary number, not the exact decimal value you typed.
  • The error is usually tiny, but rounding can amplify it when a value lands just below or above a tie.

Problem 2: Magnitude Precision

  • Binary64 has a 53-bit significand: 52 stored fraction bits plus one implicit leading bit for normal numbers.
  • Integers are exact only up to 9,007,199,254,740,991, which is Number.MAX_SAFE_INTEGER in JavaScript.
  • Past that point, adjacent representable numbers are more than 1 apart, so some integers cannot exist.

Some decimals never terminate in binary

A decimal fraction has a terminating binary representation if and only if, when written as a fraction in lowest terms, its denominator is a power of two. That is the central reason ordinary-looking decimal values can become approximate when stored as binary floating-point.

Decimal Lowest-term fraction Denominator Binary result
0.5 1 / 2 2 = 2^1 terminates: 0.1₂
0.25 1 / 4 4 = 2^2 terminates: 0.01₂
0.125 1 / 8 8 = 2^3 terminates: 0.001₂
0.1 1 / 10 10 = 2 * 5 repeats forever: 0.0001100110011...₂
0.2 1 / 5 5 repeats forever: 0.001100110011...₂
0.01 1 / 100 100 = 2^2 * 5^2 repeats forever

Base 10 terminates fractions whose reduced denominator only contains factors of 2 and 5. Base 2 terminates only fractions whose reduced denominator only contains factors of 2. That is why many currency-looking decimals are exact on paper but approximate in binary64.

Conversion mechanics

How 0.1 becomes a repeating binary fraction

For the integer part of a decimal number, repeated division by 2 gives binary digits. For the fractional part, the process is different: repeatedly multiply the fraction by 2 and record the integer part each time.

Step Fraction * 2 Next binary digit Remaining fraction
1 0.1 * 2 = 0.2 0 0.2
2 0.2 * 2 = 0.4 0 0.4
3 0.4 * 2 = 0.8 0 0.8
4 0.8 * 2 = 1.6 1 0.6
5 0.6 * 2 = 1.2 1 0.2
6 0.2 * 2 = 0.4 0 0.4
7 0.4 * 2 = 0.8 0 0.8
8 0.8 * 2 = 1.6 1 0.6

The remainder sequence repeats, so the binary digits repeat: 0.1 base 10 = 0.00011001100110011... base 2. A binary64 number has only 53 significant binary bits, so it stores the nearest finite approximation.

How the two problems connect

Scaling decimal places consumes magnitude

A common workaround is to multiply by 100, 10,000, or 100,000,000, do integer-like arithmetic, then divide back. That only works while the scaled intermediate values still fit safely inside the 53-bit integer envelope.

Real example: suppose two 4dp amounts are both 45,035,996.2738. Scaling each by 10,000 gives 450,359,962,738. If an implementation scales both operands again while adding or subtracting, the combined intermediate is about 9,007,199,254,760,000, which is already above JavaScript's exact integer limit of 9,007,199,254,740,991.

Scaling Risk

This is not a JavaScript problem

JavaScript is an easy place to see the issue because the default number type is a binary64 floating-point value. But the underlying problem is IEEE-754 binary floating-point arithmetic, not a weakness unique to JavaScript.

The same family of issues appears in Python, Java, C, C++, C#, Go, Ruby, PHP, Swift, Kotlin, Scala, Rust, R, MATLAB, Julia, Lua, Perl, Objective-C, TypeScript, Visual Basic, Fortran, and most SQL engines whenever they use binary floating-point types such as double, float, real, or binary_double.

Some platforms also provide decimal types, such as Java BigDecimal, C# decimal, Python Decimal, SQL DECIMAL, or IBM decNumber. Those are different arithmetic models. The lesson here is about what happens when a decimal business problem is forced through binary floating-point.

Why finance is different

Being off by one cent is unacceptable

In many engineering domains, a tiny floating-point error is harmless. A physics simulation, animation, chart, or sensor reading often tolerates approximation. Financial software is different because the value is not just a measurement; it is money, a contract, a ledger entry, a tax amount, a commission, or a customer balance.

If a calculation should produce 10.00 and the system books 9.99 or 10.01, the result is wrong even if the error is "only" one cent. Across many users, trades, refunds, invoices, or currency conversions, small errors can become reconciliation breaks, customer disputes, regulatory issues, or manual adjustment work.

The goal is not merely to display a nice-looking number. The goal is to apply the exact business rule, with the agreed precision and rounding policy, and to make reversals and audits reproduce the same amounts.

Finance-Specific Rounding Lessons

  • Multiplying by a scale, applying Math.round, then dividing back is not bulletproof. The intermediate value can already be slightly below or above the decimal you intended.
  • Adding Number.EPSILON can fix some examples, but it is not a proof of correctness. It can still fail for other values and magnitudes.
  • Financial systems must care about rounding policy: half-up, half-down, half-even, floor, ceiling, away-from-zero, and towards-zero do not mean the same thing.
  • Reversals and cancellations are especially dangerous. Mirroring a positive calculation as negative may not round symmetrically unless the policy and arithmetic model support that.
  • For ledger, invoice, tax, commission, FX, rebate, and refund workflows, use a decimal arithmetic model or a rigorously bounded integer model with explicit rounding rules.
